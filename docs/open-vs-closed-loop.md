## 1. 一句话区别

| | 闭环并发（closed-loop） | 开环恒定 QPS（open-loop） |
|---|---|---|
| 触发方式 | 默认（不设 `--qps`） | 设了 `--qps` |
| 加压方式 | 限制**在途** N 个，一个返回才补下一个 | 按**固定速率**发车，不等前一个返回 |
| 控制参数 | `--concurrency` | `--qps`（+ 可选 `--duration`） |
| 回答的问题 | 「N 路并发下能榨出多少吞吐？」 | 「稳定 X QPS 的流量，服务器扛不扛得住？」 |
| 类比 | 停车场：车位满了就在门口等 | 高速收费站：车按固定车流量来，堵了就排队 |

> **要点**：闭环的负载**跟着服务器快慢自动收缩**；开环的负载**由你设定、与服务器状态无关**。这决定了它们测出的尾延迟含义完全不同（见 [§3](#3-为什么必须有开环coordinated-omission)）。

## 2. 两种模型详解

### 2.1 闭环并发（closed-loop）

**机制**：用 `Semaphore(concurrency)` 限制同时在途的请求数。任一请求返回后，才放行下一个进入。因此在途数**恒等于**并发上限（除去收尾阶段）。

**测的目标**：
- 固定 N 路并发时的**饱和吞吐**（QPS / TPS）。
- 逐档抬高并发扫出**吞吐拐点**（QPS 不再增长、延迟陡增的那一档）。
- 单请求在特定并发压力下的延迟分布。

**特点**：
- 服务器一变慢，客户端自动少发 → 负载自我调节，**不会把服务器压垮到雪崩**。
- 天然适合「找最优并发配置」这类容量规划。

**局限**：会**低估尾延迟**（下节详述）。

### 2.2 开环恒定 QPS（open-loop）

**机制**：按目标到达率 `qps` 定时发车（`target = t0 + (i+1)/qps` 对齐时间戳、避免累积漂移），**不等**前一个请求返回。服务器处理不过来时，在途请求持续积压。

- 连接池**不设上限**（`max_connections=None`）：否则超额请求会在连接池里排队，等于把开环偷偷退化成闭环，积压被悄悄吸收就测不出来了。
- 信号量不参与限流，仅用于统计在途水位。
- `qps + duration` → 总请求数 = `qps × duration`（对齐传统压测工具语义）。

**测的目标**：
- 给定**稳定到达率**下服务器能否稳住（真实生产流量往往就是恒定 QPS，而非恒定并发）。
- 暴露**真实排队与尾延迟**：请求积压体现在「在途峰值」上。
- 找**可持续 QPS 上限**：最后一个「实际完成 QPS ≈ 目标 QPS 且积压不发散」的档位。

**特点**：能压出闭环压不出的雪崩/积压场景。

## 3. 为什么必须有开环：coordinated omission

这是闭环模型的**固有缺陷**，也是当初给 llmeter 补开环模式的核心原因。

> **Coordinated Omission（协同遗漏）**：闭环下，服务器一卡顿，客户端因为「要等上一个返回」而**自动停止发送新请求**。于是那些「本该在卡顿期间到达、并经历长排队」的请求根本没被发出——它们的长延迟从统计里消失了。结果：**P95/P99 被系统性低估**，报告一片绿，线上却在抖。

开环不等返回、按既定速率硬发，卡顿期间的请求照样到达并排队，长延迟被如实记录。**要测真实用户体验的尾延迟，必须用开环。**

## 4. 怎么选

| 你的目标 | 选哪个 |
|---|---|
| 找最优并发配置、做容量规划 | **闭环**（`--concurrency` 扫梯度） |
| 验证「能否稳定承接 X QPS 流量」 | **开环**（`--qps`） |
| 测真实尾延迟 / SLA（P95、P99） | **开环**（避免 coordinated omission） |
| 探吞吐上限（榨干服务器最大 QPS） | **闭环**（高并发档看 QPS 峰值） |
| 探承载拐点（多大流量开始崩） | **开环**（QPS 阶梯看积压何时发散） |
| 复现线上恒定流量的表现 | **开环** |

> 实践中两者常配合：先用**闭环**扫出吞吐上限，再用**开环**在该上限附近验证「这个 QPS 下尾延迟和积压是否可接受」。

## 5. 用法与配置

### 命令行（chat 单次）

```bash
# 闭环：20 路并发跑 200 个请求
python bench.py chat -f config/config.yaml -c 20 -n 200

# 开环：稳定 16 QPS 压 30 秒（= 480 个请求）
python bench.py chat -f config/config.yaml --qps 16 --duration 30

# 开环：不设 duration，则按 qps 速率发 -n 个请求
python bench.py chat -b ... -k ... -m ... --qps 8 -n 500
```

> ⚠️ 设了 `--qps` 即切开环，此时 `--concurrency` **不再限流**（也不再决定连接数）。

### 场景配置（scenarios，QPS 阶梯）

参见 [`config/qps-openloop.yaml.example`](../config/qps-openloop.yaml.example)（复制为 `config/qps-openloop.yaml` 后填入自己的连接信息）：场景里出现 `qps` 即切开环，`duration` 可放 `defaults` 共享。

```yaml
defaults:
  duration: 30          # 每档 30s；总请求数 = qps × 30
  stream: true          # 必须流式，否则测不到 TTFT
  retries: 0            # 开环测承载力：重试会掩盖真实失败率，关掉
scenarios:
  - {name: QPS-2,  qps: 2}
  - {name: QPS-4,  qps: 4}
  - {name: QPS-8,  qps: 8}
  - {name: QPS-16, qps: 16}
  - {name: QPS-32, qps: 32, timeout: 120}
```

```bash
cp config/qps-openloop.yaml.example config/qps-openloop.yaml      # 首次使用先复制并填 base_url/api_key/model
python bench.py scenarios -f config/qps-openloop.yaml            # 全量阶梯
python bench.py scenarios -f config/qps-openloop.yaml -s "QPS-"  # 只跑 QPS 组
```

## 6. 结果判读

报告会根据模式自动区分展示：

| 列 | 闭环 | 开环 |
|---|---|---|
| **目标QPS** | `—` | 设定的到达率，如 `16` |
| **并发** | 设定的并发上限，如 `8` | `~N` 实测**在途峰值**（积压水位，带 `~` 前缀表明非设定值） |
| **QPS** | 实测完成吞吐 | 实测完成吞吐（与目标对比看是否跟得上） |

**开环读法**（找可持续 QPS 拐点）：

| 现象 | 结论 |
|---|---|
| 实际 QPS ≈ 目标 QPS，`~在途峰值` 平稳，成功率高 | ✅ 该 QPS 服务器扛得住 |
| 实际 QPS < 目标 QPS，`~在途峰值`持续攀升，尾延迟炸 | ❌ 已过承载上限，**这一档就是拐点** |

> 注意：开环 `wall` 含收尾排空时间，故**实际完成 QPS 常略低于目标**，属正常。真正的告警信号是「积压发散 + 尾延迟陡增 + 成功率跌」。

**闭环读法**：抬并发时 QPS 不再增长、P95 陡升的那一档即吞吐拐点，最优并发取拐点前一档。详见 [test-scenarios.md §4](test-scenarios.md)。

### 6.1 为什么「QPS 2」会显示「在途 ~22」？—— Little's Law

开环下常见的困惑：明明只设了 `qps=2`，报告却显示在途峰值 `~22`。**这不是 bug，二者也不等价。** 它们由排队论的利特尔法则绑定：

```
平均在途数 L  =  到达率 λ (你设的 QPS)  ×  平均单请求耗时 W
```

以压 `~10k token` 超长输入为例：λ = 2 req/s，单请求端到端约 W ≈ 11s，则 L = 2 × 11 ≈ **22**。所以 `~22` 不是并发设置，而是「每秒来 2 个 × 每个处理约 11 秒」自然堆出来的在途量。

| 概念 | 含义 | 谁决定 |
|---|---|---|
| **QPS**（油门）| 发车速率，每秒塞几个新请求，不管处理完没 | **你设定** |
| **在途数**（转速）| 同一时刻服务器手上正在处理的请求数 = 积压水位 | **被动**，由服务器速度决定 |
| **W**（传动比）| 单请求耗时；服务器越慢 W 越大，在途越高 | 服务器 |

**和闭环的本质区别**：闭环 `concurrency=22` 是你把在途数**钉死**在 22（一个回来才补一个），永远不会积压；开环 `qps=2` 只管发车速率，在途数**随服务器快慢浮动**——服务器变慢 → W 涨 → 在途自己往上爬。因此：

- 若 `~在途` 稳定不涨、成功率高 → 服务器能稳稳消化这个负载。
- 若继续抬 QPS，`~在途` 涨得**比线性还快**（W 也在恶化）→ 已过拐点。这正是闭环测不出、开环专门要暴露的信号。

> 一句话：**QPS 是油门，在途数是发动机实际转速，W 是传动比**，三者由 Little's Law 绑定，不是同一个东西。

## 7. 常见误区

| 误区 | 纠正 |
|---|---|
| 「开环时 `concurrency=10` 是不是限了 10 并发？」 | **不是**。开环下 `concurrency` 完全不生效——不限流、不定发车、不设连接数。真正的并发是实测「在途峰值」，由服务器速度 vs 到达率决定。 |
| 用闭环测 SLA 尾延迟 | 会被 coordinated omission 低估 P99，改用开环。 |
| 开环时给连接池设上限 | 会让超额请求在池里排队，退化成闭环，测不出真实积压。llmeter 开环已强制不设上限。 |
| 开环高档「实际 QPS 追不上目标」当成 bug | 那正是**承载上限**的信号，是预期数据点。 |
| 开环开着 `retries` | 重试会掩盖真实失败率与积压，测承载力时应设 `retries: 0`。 |
