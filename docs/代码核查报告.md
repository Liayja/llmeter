# llmeter 项目代码核查报告

> 核查日期：2026-09-24
> 核查范围：核心压测引擎（`bench.py` / `src/`）、FastAPI 后端（`app/`）、新增三大模块（多模态 / 路由检测 / 一致性）、Vue3 前端（`app/web/`）、项目工程化
> 代码规模：约 7,000 行 Python + Vue3 前端

## 总体结论

整体架构清晰、分层合理，安全意识（密钥脱敏、成本闸门、媒体校验、SSE 生命周期管理）总体在线。但存在 **2 个真实可利用的安全漏洞**、**若干影响报告可信度的正确性 bug**，以及一批性能热点和大量可消除的重复代码。

**威胁模型前提**：平台默认绑定 `127.0.0.1` 且**无任何身份认证**。下列安全问题在通过 `--host 0.0.0.0` 暴露到网络后才真正可被利用；若计划暴露，需先补上身份认证。

**建议修复顺序**：
1. P0 两个安全漏洞（若会暴露到网络，先补认证）
2. #3 除数 bug + #4/#5 判定逻辑（直接影响结论正确性）
3. #8 WAL/异步化 + #9 O(n²)（影响压测本身可信度）
4. 抽共享 SSE/轮询层消除重复
5. 补测试与 CI

## 🔴 P0 · 安全（应优先修）

### 1. `prompt_file` 任意文件读取并外泄
- **位置**：`app/services/runner_bridge.py:21-29`、`app/routers/route_probe.py:60-68`；入口 `app/routers/tasks.py`、`app/routers/scenarios.py`
- **问题**：用户可控的 `prompt_file`，绝对路径直接使用、相对路径拼接 `PROJECT_ROOT`，无目录白名单校验。文件内容会被当作 prompt **发送到同样用户可控的 `base_url`**。
- **危害**：构成「读取任意本地文件 + 外泄到攻击者服务器」的完整链路。
- **修复**：拒绝绝对路径；`(PROJECT_ROOT / fp).resolve()` 后用 `Path.is_relative_to(PROJECT_ROOT/prompts)` 校验，越界抛 400。同理约束 `output_dir`（`tasks.py:38`）防止任意目录写入/覆盖。

### 2. 多模态远端抓取 SSRF 可绕过 + 无流式大小上限
- **位置**：`app/services/multimodal/media.py:131-201`
- **问题**：
  - `_ensure_remote_url` 仅对**字面 IP** 判断内网/回环，域名解析到内网 IP（如指向 `169.254.169.254` 的域名）直接放行；
  - `_fetch_remote` 使用 `follow_redirects=True` 且下载时**不再校验**，一个通过校验的公网 URL 可 302 跳转到云元数据 / 内网地址；
  - `response.content` 先全量下载再判 `MM_MAX_MEDIA_BYTES`（20MB），几百 MB 文件会先进内存 → 大小限制形同虚设。
- **危害**：SSRF 探测/读取内网与云元数据；超大 URL 致内存膨胀。
- **修复**：`follow_redirects=False` 或逐跳校验每个 redirect 目标 IP；下载前预检 Content-Length，用 `client.stream()` 边读边计数、超限即中断；解析 DNS 后对最终 IP 复查私网/保留地址（含 `0.0.0.0`）。

## 🟠 P1 · 正确性 Bug（污染报告结论）

### 3. `avg_input_tokens` 除数用错
- **位置**：`src/engine.py:208-209, 237`
- **问题**：分子只累加成功请求的 `input_tokens`，分母却用 `len(results)`（含失败/超时），与相邻 `avg_output_tokens`（除 `len(ok)`）口径不一致。有失败时输入规模被系统性低估，直接污染对比表「实际入Token」列（`output.py:198`）及输入阶梯斜率分析。
- **修复**：改为 `round(in_tokens / len(ok)) if ok else 0`。

### 4. 一致性判定混用「绝对正确」与「相对等价」
- **位置**：`app/services/parity/judge.py:100-131`
- **问题**：`system_role`、`max_tokens_compliance` 只对候选做绝对判定，未与基线比较。若官方基线自身也「违规」，候选与基线**行为一致**却被判 `fail` → 拉低 D1 `pass_rate` → 产生假「不等价」。
- **修复**：改为候选 vs 基线的相对判定（参考已正确实现的 `reasoning_field`：比较 `base_has` 与 `cand_has`）。

### 5. 路由检测分组阈值造成假阴性
- **位置**：`app/services/route_probe/analysis.py:5, 18, 83-88`
- **问题**：`_group` 要求「≥3 次且占比≥3%」才算一组，承接约 2% 流量的备用后端指纹被过滤 → 退化为 `SINGLE_ROUTE`，恰好漏掉「偶发路由到异构后端」这一核心检测目标。且 `remote_ip` 被纳入强指纹，在 keep-alive/负载均衡下同一逻辑路由的对端 IP 本会变化，易误判 `EDGE_VARIANCE_LIKELY`。
- **修复**：channel/model 等强指纹维度不设 `min_ratio` 硬门槛（1-2 次异构也应展示，仅置信度权重区分）；`remote_ip` 与 server/via 分离，降级为更弱的提示。

### 6. 前端异步竞态显示错位数据
- **位置**：`app/web/src/views/ResultsView.vue:57-65`；同类 `ParityView.vue:213`、`RouteProbeView.vue:195`、`MultimodalView.vue:225` 的 `open*` 函数
- **问题**：快速切换列表项时，后发请求被先发响应覆盖，高亮项与详情面板不一致，用户无法察觉看的是错报告。
- **修复**：返回后校验 `id === selectedId.value` 再赋值（请求令牌模式）。

### 7. 流式路径丢失 finish_reason
- **位置**：`app/services/multimodal/runner.py:224`
- **问题**：流式分支 `body` 恒为 `None`（仅非流式 179 行赋值），`_finish_reason_hint(body)` 恒返回 `""`。
- **修复**：复用 `route_probe/executor.py:151` 在流式 chunk 中采集 `finish_reason` 的逻辑。

## 🟡 P2 · 性能

### 8. SQLite 同步调用阻塞事件循环 + 未开 WAL
- **位置**：`app/db.py:263-334`；调用点遍布 `route_probe`/`parity`/`multimodal` 的 runner/executor
- **问题**：阻塞式 sqlite 调用直接跑在事件循环线程上，高并发下每个请求完成后的同步写库阻塞所有协程（含 SSE 心跳），抵消并发收益；三模块可并行且无全局串行锁，默认 rollback 模式下易 `database is locked`（`timeout=10` 只是拖延）。
- **修复**：启动时 `PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL;`；DB 调用包 `asyncio.to_thread` 或引入单独 writer 队列。

### 9. 进度上报整体 O(n²)
- **位置**：`src/engine.py:503-607`
- **问题**：每完成 1 个请求就调用 `_emit_progress`，对 `self.results` 做约 7 次全量遍历；`_finish_times` 无界增长且每次线性扫描滑动窗口；`_pct` 每次重新 `sorted` 同一列表（`lat` 连排 9 次、`ttfts` 8 次）。大 N / 高 QPS 下进度上报本身成为压测客户端瓶颈，反噬被测数据可信度。CLI 分支还会每请求刷屏打印进度。
- **修复**：全量聚合与打印只在每秒 `_monitor` 里做；`_finish_times` 改用 `collections.deque` 并裁剪窗口外时间戳；每组数据排序一次后复用；CLI 进度加节流。

### 10. 多模态 inline 内存 4-5 倍膨胀
- **位置**：`app/services/multimodal/media.py` + `app/services/multimodal/runner.py:116,199,216`
- **问题**：base64（~16MB）→ `json.dumps` 整串复制 → 挂 `item["request"] = payload`（后续未持久化，纯浪费）→ `_safe_request` 里 `copy.deepcopy(payload)` 又深拷贝一份。
- **修复**：去掉 `deepcopy`（改浅拷贝 + 替换 media part）与无用赋值；`request_size_bytes` 由 base64 长度估算而非整体序列化。

### 11. route_probe 每请求重复解密 key
- **位置**：`app/services/route_probe/runner.py:65`
- **问题**：`api_key=resolve(conn)` 在 `one_worker` 循环体内，每个请求都重新解密一次。
- **修复**：提到 `_execute` 开头算一次（参考 parity 在 router 层一次性算好 `_api_key` 的写法）。

### 12. 前端 fetch 无超时 + 轮询偏激进
- **位置**：`app/web/src/api/client.js:5-9`；`RouteProbeView.vue:184`、`MultimodalView.vue:210`（1s）、`ParityView.vue:101/121`（1.5s）
- **问题**：`fetch` 无超时，长轮询（route_probe deadline 2h）某次请求挂起会永久卡住整个轮询；固定 1s 轮询在长任务下请求量巨大（2h 上限约 7200 次）。
- **修复**：`request()` 加 `AbortController` + 超时；轮询改指数退避（1s→最多 5s）。

## 🟢 P3 · 可维护性 / 重复代码

### 后端与引擎
- **SSE 流式解析在 4 处各写一遍**：`src/engine.py`、`multimodal/runner.py:144-173`、`route_probe/executor.py:113-160`、`parity/executor.py:74-105`。逻辑差异极小，应抽成共享的 `stream_chat()` 协程。
- **非流式响应解析**（usage / `choices[0].message.content` / tool_calls）重复三份。
- **behavior 分类**：`multimodal/runner.py:32-39`（返回 `ACCEPT`）与 `parity/executor.py:28-37`（返回 `ACCEPT_AS_IS`）是同一件事却用不同枚举字符串 → 重复且不一致。
- **`_STRUCTURAL_PARAMS`** 在 `multimodal/protocols.py:4-7` 与 `parity/executor.py:20-25` 各定义一份，应合并。
- **`store.update_run` 动态列拼接** 在三个 store 中逐字节相同；runner 的 `shutdown/cancel/_tasks/_progress` 样板可提取公共基类。
- **`output.py` 打印布局**：`_print_rich` 与 `_print_plain` 重复，新增指标要改两处；纯文本对比表列宽用 `len(str(...))`，中文按 1 计宽导致终端错位（应按 `unicodedata.east_asian_width` 计算）。

### 前端
- 重复逻辑应抽 composable/utils：`formatTime`（4 处）、数字格式化（3 处）、`extra_params` JSON 校验（3 处）、Markdown 导出（2 处）、轮询骨架（3 处）。
- **`StatePanel.vue` 已实现 loading/error/empty/retry 却完全未被使用**；各 view 的 `load()` 缺 `catch`，接口失败时白屏 + unhandled rejection —— 正好用它落地统一错误态。
- 非 keep-alive 的三个 view（Parity/RouteProbe/Multimodal）任务运行中离开页面会丢失进度且不重连，建议进入时检测 running 任务恢复轮询（参考 `LoadTestView.resumeRunningTask`）。
- `LoadTestView` 首屏 `onMounted` + `onActivated` 都调 `load()` 导致重复请求；日志 `v-for` 用 index 作 key 在裁剪后 DOM 复用错位。

### 死代码 / 残留
- `src/output.py:531 _col_letter_by_header` 无任何调用，可删除。
- CLI 落盘的 `meta.chat_url` 恒为 `null`（`build_engine_config` 未回填，Web 路径已注入）—— 排查厂商自定义路径时最有用的字段失效，应回填 `engine.chat_url`。
- `parity/runner.py:103` 使用 `__import__("json").dumps(...)`，应改为文件头 `import json`。
- 旧静态前端 `app/static/`（约 1,200 行，挂载于 `/legacy`）作为 fallback 维护，是清理候选。

### 低优安全项
- `app/services/key_store.py:76-81`：短密钥（长度 ≤ 8）`mask` 泄漏前 3 位；`probe.py` 的 `_mask_auth` 同理。建议短密钥整体打码。
- 进度字典 `_progress` / `_subscribers` 任务结束不清理（`job_runner.py:122-132`、三模块 runner），进程存活期内缓慢增长。
- `multimodal/store.py:39-40` 删媒体只删 DB 行、不删磁盘文件（按 sha256 去重，删除前需判是否仍被引用）。
- `catalog.py:89-93` 等动态列名 SQL 拼接**当前安全**（字段名全来自代码内部关键字），但属脆弱模式，建议加字段名白名单断言固化不变量。

## 工程化（项目级）

- **零测试**：无 `tests/` 目录、无 pytest 配置。近 7,000 行核心逻辑（指标统计、路由指纹、一致性判定）无覆盖，重构风险高。建议至少为 `engine.aggregate`、`route_probe/analysis`、`parity/judge` 补单元测试。
- **无 CI / lint / 类型检查**：无 `pyproject.toml`、无 ruff/flake8/mypy、无 pre-commit、无 GitHub Actions。
- **依赖约束宽松**：仅用 `>=`，Python 侧无 lock 文件，可复现性弱。

## 做得好的地方（保留）

- 密钥不落明文快照，`Authorization` 头不写入持久化 payload，DPAPI 缓冲区引用处理正确。
- httpx client 全程 `async with` 正确关闭；文件句柄均用 `with`；`CancelledError` 不会被 `except Exception` 吞掉。
- SSE 的 `subscribe/unsubscribe` 在 `finally` 成对出现，前端 EventSource/轮询在 `onBeforeUnmount` 正确清理，无连接级泄漏。
- 全前端无 `v-html`/`innerHTML`，JSON 经 `<pre>{{ }}</pre>` 文本插值渲染，无 XSS 面。
- route_probe/multimodal 有成本与体积上限校验、MIME 嗅探与声明一致性校验、结构化参数保护、stale run 恢复等，安全意识总体不错。
