# llmeter 与业界压测工具对比分析

> 对比对象：**EvalScope perf**（阿里 ModelScope 官方文档）、**GuideLLM**（vLLM 官方 SLO-aware 压测平台，即用户所指的 "guildllm"）、以及 LLMPerf / vLLM benchmarks 等基线。
> 分析日期：2026-08-13。
> 资料依据：
> - EvalScope 压测官方文档（zh-cn）：https://evalscope.readthedocs.io/zh-cn/latest/user_guides/stress_test/index.html （含 quick_start / parameters / examples / multi_turn / sla_auto_tune / speed_benchmark / vs_vllm_bench / custom 全部子页）
> - GuideLLM 官方 README / metrics / architecture 文档（GitHub vllm-project/guidellm）
> - llmeter 项目源码与 docs/

---

## 1. 工具定位差异

| 维度 | llmeter（本项目） | EvalScope perf | GuideLLM |
|------|-------------------|----------------|----------|
| 定位 | 轻量自用压测脚本（3 文件 ~2000 行） | 一站式评测框架的压测子命令 `evalscope perf` | SLO-aware 压测/容量规划平台 |
| 覆盖接口 | OpenAI 兼容 `/v1/chat/completions` | OpenAI 兼容 + 本地 vLLM/Transformer + Embedding/Rerank | OpenAI 兼容 + vLLM 原生 + WebSocket 音频 |
| 压测类型 | 文本单轮 chat | 单轮/多轮/多模态/Embedding/Rerank/生产流量回放 | 多模态/多轮/tool calling/trace replay |
| 数据源 | 固定单 Prompt（或文件） | 数据集（random/openqa/share_gpt/workload_trace/custom 等）+ Modelscope/HF/local | HuggingFace/文件/合成/自定义/Mooncake trace |
| 客户端架构 | 单进程 asyncio | asyncio + SQLite 缓冲 | 多进程+多线程+asyncio |
| 报告 | 终端表格 + JSON/MD/CSV/Excel | 终端 + 多分位表 + wandb/swanlab/clearml + progress.json | console + json/csv/html |

结论：llmeter 不是要与全栈平台对齐，它的价值在"针对第三方 OpenAI 兼容 API 的轻量、可读、可定制"。但 evalscope 官方文档揭示了一些 llmeter 可以低成本补齐的能力（见 §5）。

## 2. 发压模型（流量模型）对比 —— 基于 evalscope 官方文档的精确对照

| 能力 | llmeter | EvalScope perf | GuideLLM |
|------|---------|----------------|----------|
| 闭环并发（背压保护） | ✅ `Semaphore(concurrency)` | ✅ `--parallel`，worker 收到响应才发下一条 | ✅ concurrent(streams) |
| 开环固定速率 | ✅ `--qps` 固定间隔 | ✅ `--open-loop` + `--rate` | ✅ throughput / constant |
| **泊松到达率**（真实突发流量） | ❌ 仅固定间隔 | ✅ **`--rate > 0` 即泊松到达**（间隔服从均值为 1/rate 的指数分布）；closed-loop 下也可用 | ✅ Poisson |
| **多速率点自动扫描** | ❌ 手动多场景 | ✅ **一次命令多个 `--rate` 值**（`--number` 等长对应），自动扫描吞吐-延迟曲线 | ✅ sweep |
| 开环连接池不设上限 | ✅（None） | ✅（parallel 内部设 INF） | ✅ |
| 预热 | ✅ `--warmup N`（默认 0） | ✅ `--warmup-num`：绝对数量 / **比例模式**（0~1 按 number 比例） | ✅ 百分比/绝对值 |
| 冷却 cooldown | ❌ | ✅ `--sleep-interval`（轮间） | ✅ cooldown 排空期 |
| **时长软退出** | ❌ 只有总请求数 | ✅ `--duration`：到点不再启动新请求、在飞的跑完 | ✅ max_duration |
| 过饱和自动检测 | ❌ | ❌ | ✅ over_saturation |
| **SLA 自动调优（二分搜索）** | ❌ | ✅ `--sla-auto-tune`（见 §4） | ✅ SLO-driven |
| 停止条件 | 仅请求数 | 请求数/时长（先到为准） | max_duration/max_requests/max_errors |

> ⚠️ 修正：上一版对比中我按 README 推测 evalscope 开环"有限"——根据官方文档，**evalscope 的开环 + 泊松 + 多速率扫描能力是完整的**，甚至比 GuideLLM 更直白（一次命令多 rate 值）。

## 3. 指标对比

| 指标 | llmeter | EvalScope perf | GuideLLM |
|------|---------|----------------|----------|
| 请求状态 | success / fail 两类 | **Succeed / Failed**（与 vLLM bench 对齐） | success / incomplete / error 三类 |
| 吞吐 | QPS、TPS（输出 tok/s） | Request throughput、Output/Total token throughput | request rate、output/total tok/s |
| 延迟分位 | P50/P95/P99（线性插值） | **默认 10/25/50/75/90/95/98/99% 多分位** | P0.1~P99.9 共 10 档 + mean/median/mode/variance/std |
| TTFT | Avg/P50/P95 + ttft_answer | TTFT（流式必开 `--stream` 才能测） | TTFT 全分布 |
| TPOT | 有（流式/非流式定义不同） | TPOT | TPOT 全分布 |
| ITL | Avg/P50/P95/Max | ITL | ITL 全分布 |
| 推理指标 | **thinking_time / reasoning_tokens / ttft_answer（特色）** | 有推理支持 | 未突出 |
| 单位 | s | **s**（与 vLLM 的 ms 有换算表） | ms/s 混合 |

**与 vLLM Bench 的对齐验证（evalscope 独有，值得借鉴）**：evalscope 官方提供了 `vs_vllm_bench` 文档，专门做参数对齐、一致性校验（1 并发/1 请求、50 并发/1000 请求）、指标口径与命名对照，并列出常见误差来源：
- 流式/非流式一致（避免 TTFT/ITL 口径不一致）
- `ignore_eos` / `stop` 一致（否则输出长度与 TPOT/ITL 偏差）
- 同一 tokenizer / Chat 模板
- 解码参数一致（temperature=0、top_p=1、top_k=0）
- 预热 + 同节点回环（连接池/Keep-Alive/DNS 影响 TTFT）

> llmeter 没有做这类"与基准工具对齐验证"，其流式口径（t0 在信号量后、TTFT=首有效 token、ITL=相邻 chunk 间隔、TPOT=(latency-TTFT)/(out-1)）与 evalscope/vLLM 一致，但没有文档证明。

## 4. EvalScope 独有的关键能力（llmeter 均无）

1. **SLA 自动调优**：`--sla-auto-tune --sla-variable parallel|rate --sla-params '[{"p99_latency":"<=2"}]'` —— **二分查找**自动探测"刚好不违约"的最大并发/速率；指标支持 avg/p99 的 latency/ttft/tpot + rps/tps；每组约束独立二分；每档跑 3 次取平均；number = variable × N。
2. **多轮对话压测**：`--multi-turn`，每轮成功后把模型真实回复追加上下文，评估上下文增长下的延迟/吞吐；专属指标（平均上下文轮数、KV 缓存命中率）；多轮数据集（random_multi_turn / share_gpt / swe_smith / trie trace）。
3. **生产流量回放**：`--dataset workload_trace` 按录制时间戳逐字回放真实流量（突发到达、异构请求、多模型路由），支持倍速 + 模型映射 + 输出长度对齐。
4. **数据集驱动**：`--dataset` + `--data-source modelscope|huggingface|local`，支持输入长度截断、prefix 注入；Embedding/Rerank 压测。
5. **可观测性**：wandb/swanlab/clearml 可视化、progress.json 实时进度、SQLite 缓冲落库。
6. **插件体系**：自定义数据集（`DatasetPluginBase` + `@register_dataset`）、自定义请求 API、自定义结果分析。

## 5. 测试结果准确性评估（对照 evalscope 官方口径）

### 5.1 与业界一致、llmeter 做对了的

1. **计时起点正确**：t0 在信号量之后，延迟不含客户端排队 —— 与 evalscope/vLLM 一致。
2. **开环设计正确**：固定速率发车、连接池不设上限（evalscope 同样在 open-loop 下把 parallel 设为 INF）、积压体现在在途水位 —— 正确规避 coordinated omission。
3. **token 计数优先级**：优先 API usage → tiktoken → 字符估算 —— 业界标准。
4. **重试策略**：仅瞬时错误（429/500/502/503/连接失败）退避重试，持久错误不重试 —— 合理。
5. **流式测量口径**：TTFT=首个有效 token（含 reasoning_content）、ITL=相邻内容 chunk 间隔、TPOT 流式剔除 prefill —— 与 evalscope/vLLM bench 口径一致。

### 5.2 存在系统性偏差风险的点（对照 evalscope 后重新排序）

> 状态标注：2026-08-13 已修复其中的 #1、#2、#3、#4、#6、#8，以及 #9 的"默认预热"部分（默认流式、三分类、重试透明化、开环两阶段、TPOT 口径、多分位、默认预热；#9 的"比例模式"与其余 P1/P2 项未做），详见 [CHANGELOG](CHANGELOG.md)。

| # | 问题 | 影响 | evalscope 的做法 |
|---|------|------|------------------|
| 1 | **默认 retries=2 且重试成功计入成功** | 限流被掩盖，成功率/QPS 虚高 | 与 vLLM bench 对齐时建议"参数一致、不混用"，重试语义需显式控制 |
| 2 | **默认 stream=False** | 不开流式则 TTFT/ITL 不可测，且用户易忘 | **evalscope 默认 stream=True**（"需要启用以测量 TTFT"） |
| 3 | 开环 wall 含收尾排空时间 | 实际 QPS 系统性略低，易误读为拐点 | `--duration` 软退出 + `--sleep-interval` 轮间冷却 |
| 4 | 失败只有 success/fail 两类 | 超时与 4xx/5xx 混在一起，SLA 解读失真 | Succeed/Failed 分类（与 vLLM bench 对齐） |
| 5 | 流式无 usage 回退时 token 为字符估算 | TPS/total_tokens 误差 20~50% | 支持 `ignore_eos` 对齐输出长度，减少误差 |
| 6 | TPOT 流式/非流式定义不一致 | 跨模式 TPOT 不可比 | 统一流式口径（文档强调勿混用非流式） |
| 7 | 单一固定 Prompt + 默认不破 prefix cache | TTFT/延迟被缓存压低，不代表真实负载 | 数据集驱动 + 输入长度随机采样 + 多模态 |
| 8 | 分位只有 P50/P95/P99 | tail 分析粒度不够 | 默认 10/25/50/75/90/95/98/99% 多分位 |
| 9 | 预热默认 0 且无比例模式 | 冷启动污染首批 TTFT；sweep 多档时不方便 | `--warmup-num` 支持比例模式 |
| 10 | Windows asyncio.sleep 调度精度 ~15ms | 开环高 QPS 档到达率抖动 | 官方建议同节点回环测试；客户端调度更精确 |

### 5.3 已正确处理、不会影响准确性的

- 闭环连接池上限 = concurrency×2、开环不设上限。
- 超时分离（connect/write/pool 短超时 + read 独立超时），长生成不误判。
- GC 关闭 + 水位监控，减少客户端干扰。
- 百分位线性插值、错误摘要截断。

## 6. 优化建议（按优先级，参照 evalscope 官方能力）

### P0 — 修准确性（改动小、收益大）
1. ✅ **已实现（2026-08-13）** 默认 stream=True（与 evalscope 一致），TTFT/ITL 开箱即测；新增 `--no-stream` 显式关闭。
2. ✅ **已实现（2026-08-13）** 失败三分类：success / incomplete（超时/连接中断，status_code=0）/ error（HTTP 4xx/5xx）分别计数，报告与 JSON 同步。
3. ✅ **已实现（2026-08-13）** 重试单独计数：新增 `retried` 指标（含每条请求的 retried 标记）；文档建议真实成功率跑法用 `retries: 0`。
4. ✅ **已实现（2026-08-13）** 开环 wall 口径修正：`--duration` 已支持时长软退出；新增发车/排空两阶段耗时（`dispatch_phase` / `drain_phase`）与 `qps_dispatch` 实际发车速率，QPS 缺口可归因。

### P1 — 对齐业界功能（中等工作量）
5. ✅ **已实现（2026-08-13）** 多分位输出：指标增加 P75/P90/P98/P99.9（TTFT 另加 P99/P99.9），JSON/单次报告/对比表同步。
6. **Poisson 到达率**：开环增加 `--arrival poisson`（rate 为均值，指数分布间隔）。
7. **多速率点扫描**：开环 `--qps` 支持多值（空格分隔），一次命令跑完整 QPS 阶梯并自动对比。
8. **SLA 自动调优**：`--sla-params` + 二分搜索找最大并发/速率（对标 evalscope sla-auto-tune / GuideLLM SLO）。
9. **数据集驱动**：支持目录/文件列表随机采样 prompt + 输入长度截断（对标 `--dataset`）。
10. **预热比例模式**：`--warmup` 支持 0~1 比例（对标 `--warmup-num`）。

### P2 — 扩展能力（按需）
11. **多轮对话压测**：`--multi-turn`，真实回复追加上下文（对标 evalscope 多轮）。
12. **生产流量回放**：`--trace` 按时间戳回放 JSONL（对标 workload_trace）。
13. **可观测性**：progress.json 实时进度 + 可选 wandb 集成。
14. **插件体系**：数据集/请求/结果分析三类自定义入口（对标 DatasetPluginBase）。

## 7. 结论

- **合理性**：作为"第三方 OpenAI 兼容 API 轻量压测工具"，llmeter 架构与方法学合理 —— 双发压模型设计正确、核心指标测量口径与 evalscope/vLLM bench 一致、推理模型指标（ttft_answer/thinking_time）是差异化特色、输出体系完整。
- **准确性**：核心指标测量方法正确可信；系统性偏差风险集中在：默认非流式（TTFT 不可测）、默认重试污染成功率、开环 wall 含排空、失败分类粗糙、单 Prompt + prefix cache。
- **与 evalscope 的关键差距**：evalscope 官方文档确认它拥有 llmeter 完全缺失的 **泊松到达、多速率扫描、SLA 二分自动调优、多轮压测、生产流量回放、多分位输出、比例预热、时长软退出**，且做了 **与 vLLM Bench 的一致性对齐验证**（这是"结果可信"的最好证明方式，llmeter 可借鉴：用本地 mock 服务与已知基线工具交叉验证）。
- **一句话**：llmeter 的方法学站得住，缺的是"负载真实度"（泊松/数据集/回放）与"自动化闭环"（SLA 扫描/软退出/回放）。**P0 四项与 P1 多分位已随 2026-08-13 更新实现**（见 [CHANGELOG](CHANGELOG.md)）；剩余差距集中在泊松到达率、多速率扫描、SLA 自动调优、数据集驱动等自动化能力。
