# 路由检测功能说明

> 适用模块：llmeter → 路由检测
>
> 作用：在没有上游渠道信息的前提下，通过客户端观测数据推断同一个模型或 Key 是否命中多个后端路由。
>
> 重要说明：这是黑盒推断，不是读取上游渠道表，不能承诺 100% 证明渠道数量。

## 1. 功能定位

路由检测用于回答：

- 同一个模型、同一个 Key，请求是否总是落到同一种后端指纹？
- 是否出现稳定的多组 `prompt_tokens`、模型标识、响应头或延迟分布？
- 失败是否集中在某一组指纹上？
- 更像是随机分流、故障切换，还是客户端/入口网络不稳定？
- 这些判断有哪些原始证据，置信度有多高？

它不是压测：不测 QPS，不追求高并发，不用失败数量直接证明多路由。

## 2. 与现有模块的关系

| 模块 | 目标 |
|---|---|
| 压测 | 多并发测性能 |
| 一致性基准 | 比较官模与第三方模型行为 |
| 多模态测试 | 单次图片/视频请求可行性 |
| 路由检测 | 推断客户端可见范围内是否存在多个后端路由指纹 |

路由检测直接复用资产库中的连接和模型，不需要重复填写 Base URL、密钥和模型 ID。

## 3. 使用前准备

1. 在「资产库 → 连接」配置 Base URL 和密钥。
2. 在「资产库 → 模型」添加目标模型并绑定连接。
3. 在「路由检测」选择该模型。
4. 建议先运行「连接路由快速检测」，再按需运行 Tokenizer 指纹、标准确认或长输入复现。

## 4. 预设说明

| 预设 | 请求量 | 并发点 | 流式 | 用途 |
|---|---:|---:|---|---|
| 连接路由快速检测 | 30 | 1 | 否 | 低消耗检查连接、入口和错误指纹 |
| Tokenizer 指纹 | 30 | 1 | 否 | 使用相同 Prompt，重点观察 `prompt_tokens` |
| 标准确认 | 100 | 1 | 否 | 增加样本量，确认稳定分组 |
| 长输入/流式复现 | 30 | 1 | 是 | 复现长输入、超时和流式中断，成本较高 |

预设只是默认参数，页面中的所有参数都可以自定义。页面会直接显示“每并发点请求数”；
修改该值后预设会切换为「自定义」。

### 内置 Prompt

| 预设 | 内置 Prompt 的作用 |
|---|---|
| 连接路由快速检测 | 短 JSON 指纹：`{"probe":"Q7K2M9","ok":true}` |
| Tokenizer 指纹 | 混合中文、英文、JSON、代码、emoji 和数字 |
| 标准确认 | 使用短 JSON 指纹，增加请求数 |
| 长输入/流式复现 | 不设置内置 Prompt，需要选择 `prompts/*.txt` 文件 |

提示：不同 Prompt 的 `prompt_tokens` 不能直接放在同一组比较。每次检测只使用一个 Prompt，
报告中会保存 Prompt 的 SHA256 和摘要，便于确认两次检测是否使用了同一份输入。

## 5. 主要参数

| 参数 | 说明 | 建议 |
|---|---|---|
| 每并发点请求数 | 每个并发点发送多少次请求 | 默认 30，确认时 100，长输入复现 30～50 |
| 并发点 | 例如 `1,10` | 先用 1，再测试 5、10、20 |
| Prompt | 固定测试文本 | 路由指纹测试建议使用短文本 |
| Prompt 文件 | 使用 `prompts/*.txt` | 分析长输入失败时使用 |
| max_tokens | 最大输出长度 | 连接路由 4，标准确认 8，长输入复现 64 |
| temperature | 采样温度 | 建议固定为 0 |
| 超时 | 单请求读取超时 | 长输入和流式建议 300 秒 |
| extra_params | 模型额外参数 | 如 `thinking`、`reasoning_effort` |
| 流式 | 是否使用 SSE | 分析读取和流式错误时开启 |
| 唯一前缀 | 每个请求加随机前缀 | 连接检测开启；Tokenizer 指纹关闭 |
| HTTP/2 | 是否启用 HTTP/2 | 默认关闭；开启后错误增多则关闭 |
| logprobs | 是否请求 logprobs 指纹 | 默认关闭；接口支持时可用于检测量化/推理栈差异 |

### 为什么默认不重试

路由检测要观察每一次首次请求的真实结果。如果客户端自动重试：

- 首次失败会被成功重试掩盖；
- 一个逻辑请求可能多次命中不同路由；
- 成功率、延迟和指纹分组都会失真。

因此当前模块默认不重试。需要分析瞬时网络错误时，可以另外使用压测模块。

### Token 成本和保护

路由检测的成本近似为：

```text
总请求数 × (Prompt Token + 输出 Token)
```

默认「连接路由快速检测」使用短 Prompt 和 `max_tokens=4`，通常只消耗几百到几千 Token。

页面上会显示预估请求数、预估输入 Token 和预估总 Token。默认规则：

```text
超过 100,000 预计 Token：界面提示高成本，需要勾选“允许高成本检测”
超过 1,000,000 预计 Token：后端默认拒绝，避免误跑长 Prompt 的大量请求
```

长 Prompt 不适合做默认路由指纹检测。`input-10k.txt` 或 `input-20k.txt` 建议只在复现长输入超时和流式中断时使用，并且只跑少量请求。

## 6. 平台采集什么

### 请求侧

- `client_request_id`
- 请求序号、并发点
- 模型名、请求体和实际 URL
- HTTP 版本

### 响应侧

平台尽量采集：

```text

via
cf-ray
x-request-id
request-id
x-channel-id
x-upstream-id
x-served-by
openai-processing-ms
x-envoy-upstream-service-time
x-ratelimit-*
```

如果上游不返回某字段，该字段会留空，不影响其他指纹检测。

### 模型行为字段

```text
response.model
system_fingerprint
usage.prompt_tokens
usage.completion_tokens
usage.cached_tokens
reasoning_tokens
finish_reason
output_hash
```

### 时间和错误字段

```text
remote_ip
TTFE：首个 SSE 事件时间
TTFT：首个内容 token 时间
latency：总耗时
status_code
error_type
error_phase
response_received
```

## 7. 指纹维度

| 维度 | 字段 | 强度 | 说明 |
|---|---|---|---|
| 渠道指纹 | `x-channel-id`、`x-upstream-id` | 最高 | 出现多组时最有价值 |
| 模型指纹 | `response.model`、`system_fingerprint` | 高 | 同一模型出现多组，可能后端实现不同 |
| Tokenizer 指纹 | `usage.prompt_tokens` | 高 | 同一 Prompt 出现多组，可能 tokenizer/模板不同 |
| `logprobs` 指纹 | logprobs 哈希 | 高 | 需要接口支持，对量化/推理栈差异敏感 |
| 入口指纹 | `server`、`via`、`remote_ip`、HTTP 版本 | 中 | 可能是 CDN、边缘节点或网关入口 |
| ID 前缀 | 响应 `id` 的稳定前缀 | 中 | 可能来自上游，也可能由网关生成 |
| 错误阶段 | `error_phase` | 中 | 区分连接、发送、读取和流式中断 |
| 延迟 | TTFE、TTFT、总延迟 | 辅助 | 不能单独证明渠道差异 |

同一 Prompt 正常情况下应满足：

```text
response.model 稳定
system_fingerprint 稳定
prompt_tokens 稳定
```

如果这些都稳定变化，结论比“只有延迟不同”可靠得多。

## 8. 结论和置信度

| 结论 | 含义 |
|---|---|
| `SINGLE_ROUTE` | 客户端可见范围内没有发现稳定多套指纹 |
| `MULTI_ROUTE_LIKELY` | 至少两种独立指纹出现稳定多组，疑似多后端路由 |
| `MULTI_ROUTE_SUSPECTED` | 只有一种强指纹出现多组，值得继续确认，但证据还不够强 |
| `MULTI_INSTANCE_LIKELY` | ID/入口/错误等中强指纹分裂，但模型和 tokenizer 指纹基本一致 |
| `EDGE_VARIANCE_LIKELY` | IP/server/via 变化，但模型和 token 指纹一致，更像 CDN/边缘变化 |
| `CLIENT_OR_GATEWAY_UNSTABLE` | 有失败，但没有形成稳定 token、模型或响应头分组 |
| `INCONCLUSIVE` | 样本不足，或证据互相矛盾 |

置信度是证据加权结果，不是上游渠道概率：

```text
渠道响应头多组：最多 +35
模型标识多组：最多 +25
prompt_tokens 多组：最多 +25
入口指纹多组：最多 +15
错误阶段多组：最多 +10
```

建议解读：

```text
70～100：多路由证据较强
40～69：多路由待确认，建议增加采样或做 Tokenizer 指纹检测
1～39：弱证据，通常应显示 `MULTI_ROUTE_SUSPECTED`，不能单独作为结论
0：没有形成稳定分组
```

置信度为 25% 时，通常只代表一个强指纹维度出现了多组，例如
`system_fingerprint` 变化，但 `prompt_tokens` 或渠道响应头没有同步变化。此时结论应是
“疑似，但需要继续验证”，不要直接向供应商断言存在多个渠道。

## 9. 推荐使用流程

### 第一步：连接路由快速检测

```text
模型：kimi-k3
预设：连接路由快速检测
请求数：30
并发：1
stream：false
max_tokens：4
Prompt：短 JSON 指纹
```

查看是否存在多组：

- `prompt_tokens`
- `response.model`
- `system_fingerprint`
- `server`、`via`、`remote_ip`

如果都只有一组，可以继续运行「标准确认」的 100 次，而不是直接跑上千次。

### 第二步：Tokenizer 指纹

```text
预设：Tokenizer 指纹
请求数：30
并发：1
unique_prefix：false
Prompt：混合中文/English/JSON/代码/emoji
```

重点看 `usage.prompt_tokens` 是否稳定分成多组。相同 Prompt 应得到稳定 token 数。

### 第三步：标准确认

```text
每并发点请求数：100
并发点：1
```

重点比较：

- 单并发是否稳定；
- 是否持续出现相同的多组指纹；
- 延迟是否出现双峰。

### 第四步：长输入/流式复现

```text
stream：true
timeout：300
max_tokens：64
请求数：30～50
```

重点看：

- TTFE 是否出现两个峰值；
- HTTP 200 后是否没有 `[DONE]`；
- 错误是否集中在 `read` 或 `stream`；
- 是否只有某个指纹组出现流式中断。

### 第四步：多轮时间观察

在不同时间段至少做 3 轮相同测试：

```text
上午
下午
晚高峰
```

如果指纹组和时间段相关，可能存在渠道健康切换、权重变化、自动禁用或上游扩缩容。

## 10. 原始记录怎么看

在「原始探测记录」中，每个请求一行：

| 字段 | 观察方式 |
|---|---|
| 请求序号 | 按时间顺序看路由是否切换 |
| 并发 | 比较单并发和高并发 |
| HTTP | 200、4xx、5xx 或空值 |
| 模型标识 | 是否出现多个 `response.model` |
| system_fingerprint | 是否出现多个值 |
| 输入 Token | 同一 Prompt 是否出现多组 |
| 远端 IP | 是否命中不同入口 |
| 延迟 | 是否出现快/慢两群 |
| 错误阶段 | connect、read、stream 或 write |
| 错误类型 | ConnectTimeout、ReadError、RemoteProtocolError 等 |

点击「详情」可查看实际请求、响应头、usage、原始响应和错误原文。

如果结论区域点击「导出证据报告」，会下载一份 Markdown 报告，包含：

- 结论和置信度；
- 每个指纹维度的分组、次数、占比和样例请求序号；
- 原始请求摘要表；
- 使用限制和建议下一步。

报告中会带上每个指纹组的样例请求序号、客户端 Request ID、ID 前缀、
`prompt_tokens`、远端 IP、延迟和错误阶段，方便与上游日志逐条对齐。

这份 Markdown 可以直接发给上游供应商，但建议同时说明“这是客户端黑盒推断，不是渠道配置证明”。

## 11. 结果示例

### 疑似多路由

```text
结论：MULTI_ROUTE_LIKELY
置信度：85%

渠道指纹出现两组
response.model 出现两组
prompt_tokens：7094 / 9210
失败集中在第二组的 read/stream 阶段
```

解释：同一模型和 Prompt 出现了稳定多套后端指纹，建议结合上游单渠道绑定测试确认。

### 更像入口波动

```text
结论：EDGE_VARIANCE_LIKELY
置信度：30%

remote_ip 多个
server/via 多个
prompt_tokens 一致
response.model 一致
```

解释：客户端看到了多个入口，但模型和 tokenizer 指纹一致，当前证据不足以判断为多个模型渠道。

### 网络不稳定

```text
结论：CLIENT_OR_GATEWAY_UNSTABLE

连接阶段约 10 秒超时
prompt_tokens 没有多组
response.model 没有多组
```

解释：存在连接失败，但没有稳定路由指纹，更可能是客户端到网关、DNS、TLS、连接池或入口问题。

## 12. 限制

1. 上游不返回 `x-channel-id` 时，不能直接证明渠道 ID。
2. `remote_ip` 变化可能是 CDN、DNS 或边缘节点变化，不等于模型渠道变化。
3. `prompt_tokens` 变化可能是 tokenizer、模板、系统提示或模型版本变化。
4. 延迟双峰可能只是排队、缓存、负载或网络变化。
5. 只有失败数量变化、没有稳定指纹时，结论只能是“不稳定，无法确认多路由”。
6. 客户端 `retries=0` 不代表上游不会在渠道间内部重试。
7. 流式请求受代理、SSE 缓冲、读超时和 keepalive 影响。
8. 高请求量会消耗 Token，建议先跑快速预设。

## 13. 常见问题

### 为什么没有 `x-channel-id`？

很多中转站会剥离上游响应头。此时只能依赖模型、tokenizer、入口和错误阶段指纹，推断置信度会降低。

### 为什么字段都是空的？

可能是网关没有返回字段，或者请求没有收到响应。查看原始响应和错误阶段。

### 为什么很多失败却不是多路由？

失败只能证明连接或读取不稳定，不能证明请求去了不同后端。必须同时有稳定指纹分组。

### 为什么约 10 秒失败？

重点看 `error_phase=connect`，常见于连接建立超时、DNS/TLS、网关连接限制或连接池问题。

### 为什么 70～150 秒才失败？

更可能是 HTTP 连接已建立后，SSE 被代理或网关中断，或客户端读取超时。重点看 `error_phase=read/stream`、TTF 和 HTTP 状态。
