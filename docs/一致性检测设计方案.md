# llmeter 一致性检测（Parity）设计方案

> 编写日期：2026-09-24
> 对应实现：`app/services/parity/`（`cases.py` / `executor.py` / `judge.py` / `runner.py` / `store.py`）
> 定位：本文是对**已落地**一致性检测模块的权威说明书，覆盖判定模型、闸门、结论机制与数据模型；同时把《代码核查报告》中影响结论可信度的问题（#4）作为「已知缺陷 + 修正方向」内联，供后续修复对照。

## 1. 这个模块要回答的问题

用户手里有两个 OpenAI 兼容接入点：

- **官方基线（baseline）**：被认定为「正确」的那一方（如厂商官方 API）；
- **候选（candidate）**：待验证是否与官方「同一个模型 / 同一套实现」的一方（如中转站、私有化部署、第三方聚合）。

模块要回答的不是「候选答得对不对」，而是 **「候选与官方基线在协议行为与实现指纹上是否等价」**。这是一个**相对判定**问题：基线是活的参照物，不是写死的标准答案。凡是脱离基线、直接对候选做「绝对正确性」判断的地方，都是设计缺陷（见 §4.3、§8 缺陷 #4）。

### 1.1 核心设计取舍

| 取舍 | 决策 | 理由 |
|------|------|------|
| 判「文本相同」还是「行为同类」 | **行为同类** | 温度、采样、时间戳导致文本天然不同；逐字比对只会制造噪声。改为比对 tokenizer 指纹、usage 字段、协议行为类别等**低方差、强判别**的信号。 |
| 基线是标准答案还是活参照 | **活参照** | 官方模型会静默升级；把某次官方输出固化为「正确答案」会随时间失真。基线带 `created_at`，超期触发闸门提醒（§4.1）。 |
| 请求体谁说了算 | **用例完全控制** | 用例内置完整 payload，模型级 `extra_params` 中的结构字段被剥离（§3.2），保证基线与候选发出的是**逐字节可复现**的同一请求。 |
| 证据不足怎么办 | **显式「不可比」** | 宁可判「不可比 / inconclusive」也不猜。鉴权失败、限流、5xx、缺 usage 都不算模型差异（§4.2）。 |

## 2. 整体流程

```
建立基线 (baseline)                候选运行 (run)
─────────────────                 ─────────────
选连接+模型+维度                    选基线 + 候选连接+模型
   │                                  │
   ▼                                  ▼
逐用例 execute_case ──────────►  逐用例 execute_case（同一批用例）
   │  采集 status/usage/text          │
   ▼  /tool_calls/behavior_class      ▼
存 parity_baseline_items          存 parity_run_items
   │                                  │
   ▼                                  ▼
status=ready                      build_report()
                                      │
              ┌───────────────────────┼───────────────────────┐
              ▼                        ▼                       ▼
         D0 闸门校验            逐用例 judge_case          维度聚合
       (覆盖率/超期/            (pass/fail/skip/           (green/yellow/
        用例集/候选异常)         inconclusive)              red/gray)
              └───────────────────────┼───────────────────────┘
                                      ▼
                              红旗（一票否决）
                                      ▼
                    结论：等价 / 可疑 / 不等价 / 不可比 (+ 加权分)
```

代码入口：`runner.start_baseline` / `runner.start_candidate` → `_run_baseline` / `_run_candidate` → `judge.build_report`。

## 3. 用例集（`cases.py`）

### 3.1 维度划分

当前用例集 `CASE_SET = "parity-v1"`，四个维度（编号不连续是因为脱胎自更大的维度体系，`parity-v1` 只落地了判别力最强的四个）：

| 维度 | 名称 | 权重 | 判定规则 | 检测意图 |
|------|------|------|----------|----------|
| **D1** | 接口与参数语义 | 12 | `max_tokens_compliance` / `reasoning_field` / `system_role` | `max_tokens` 是否被遵守、usage 是否含 `reasoning_tokens`、system 角色是否生效 |
| **D2** | 指纹一致性 | 20 | `tokenizer_fingerprint` | 6 段固定文本的 `prompt_tokens` 是否高度一致——**最强的「是否同一套 tokenizer/模板」信号** |
| **D8** | 结构与工具调用 | 15 | `json_output` / `tool_call` | 强制 JSON、强制 function calling 是否可用 |
| **D9** | 协议健壮性 | 10 | `behavior_class` | 孤儿 tool、id 不匹配、悬空 tool_calls、并行 tool、指向不存在工具等**异常序列**下，候选的行为类别是否与官方同类 |

权重之和为 57（非 100），加权分做归一化处理（§5.3），因此权重是**相对比例**，新增维度无需重新配平到 100。

### 3.2 用例是「静态请求体 + 判定规则」

每个用例 = `{id, dimension, name, payload, judge}`。`payload` 是**完整请求体片段**，`execute_case` 在其上叠加：

```
payload = {**safe_extra, **case_payload, "model": model}
```

`safe_extra` 是模型级 `extra_params` **剔除结构字段后**的剩余项。`_STRUCTURAL_PARAMS`（`executor.py:20`）列出了所有会改变请求语义的字段（`messages`/`tools`/`max_tokens`/`temperature`/…）。被剔除的字段记入 `param_notes`，在报告里显式提示「未应用」。

> **不变量**：同一用例在基线侧和候选侧发出的请求体逐字节一致（除 `model` 字段外）。这是「相对判定」成立的前提——若两侧请求不同，任何差异都无法归因于实现差异。

### 3.3 演进方向（不在本期）

- `cases.py` 顶部注释标注了 D9 判定中「均 ACCEPT 无法排除静默修复」的局限，规划 **P2 用合法变体比对 `prompt_tokens`** 进一步判别；
- 用例目前代码内置，规划迁到数据库由界面维护（会引入 `case_set` 版本管理，与闸门的用例集一致性校验 §4.1 联动）。

## 4. 判定模型（`judge.py`）

四层：**证据有效性 → 逐用例判定 → 维度聚合 → 结论**。

### 4.1 D0 闸门（`build_report` 前段）

闸门是「这份报告能不能信」的总开关，任一条不满足即结论强制为**不可比**：

| 闸门 | 触发条件 | 语义 |
|------|----------|------|
| 用例集一致 | `baseline.case_set != CASE_SET` | 基线是旧用例集建的，不能与当前用例混比 |
| 基线覆盖率 | 有效基线证据 < 95% | 官方侧本身就没跑通，无参照物 |
| 基线新鲜度 | `age_days > baseline_max_age_days`(默认30) | 官方可能已静默升级，基线过时 |
| 候选可判性 | 存在鉴权/限流/5xx/超时的候选请求 | 候选侧是运维问题，不是模型差异 |
| 维度证据 | 任一维度聚合为 `gray`（无可判定证据） | 该维度没有可比数据 |

每条闸门都同时产出 `reasons`（为什么不可比）和 `suggestions`（怎么修），前端直接渲染给用户。

### 4.2 证据有效性：区分「模型差异」与「运维故障」

这是本模块最关键的设计——**HTTP 层故障必须与模型行为差异分离**，否则中转站限个流就会被误判成「模型不等价」。

- `_operational_failure`（`judge.py:45`）：`error` 且无状态码、或状态码 ≥500、或 ∈ `{401,403,429}` → 运维故障；
- 基线侧运维故障 → 该用例 `inconclusive`，并拉低闸门覆盖率；
- 候选侧运维故障 → 该用例 `inconclusive`，并触发闸门「候选可判性」；
- D9 是特例：`_baseline_valid` 允许基线返回 4xx（拒绝异常序列本身就是**预期行为**），其余维度要求基线 2xx。

`verdict` 四态：`pass` / `fail` / `skip`（缺字段无法比，如无 usage）/ `inconclusive`（证据不可用）。只有 `pass|fail` 进入维度通过率计算，`skip|inconclusive` 不污染分母。

### 4.3 逐用例判定规则与「相对判定」原则

| 规则 | 实现 | 是否已做相对判定 |
|------|------|:----:|
| `tokenizer_fingerprint` | `|cand−base|/base` 偏差，≤2% pass | ✅ 天然相对（对比 base 与 cand） |
| `reasoning_field` | 比较 `base_has` 与 `cand_has`，仅「官方有、候选无」判 fail | ✅ **正确范式** |
| `behavior_class` | `base_cls == cand_cls` 判 same | ✅ 相对 |
| `max_tokens_compliance` | 仅看候选 `used > limit` | ❌ **绝对判定（缺陷）** |
| `system_role` | 仅看候选中文占比 <5% | ❌ **绝对判定（缺陷）** |
| `json_output` / `tool_call` | 仅校验候选输出结构 | ⚠️ 绝对判定（可接受，见下） |

> **已知缺陷（核查报告 #4，`judge.py:100-131`）**：`max_tokens_compliance` 与 `system_role` 只对候选做绝对判定，**未与基线比较**。若官方基线自身也「违规」（例如官方也不严格遵守 `max_tokens`），候选与基线**行为一致**却被判 `fail`，拉低 D1 通过率，产生假「不等价」。
>
> **修正方向**：参照 `reasoning_field` 范式改为相对判定——
> - `max_tokens_compliance`：比较「基线是否超限」与「候选是否超限」，仅当**基线遵守而候选不遵守**时判 fail；两侧都超限视为行为一致（pass，附 param_notes 说明）；
> - `system_role`：先算基线中文占比，仅当**基线满足约束而候选显著偏离**时判 fail。
>
> `json_output` / `tool_call` 保留绝对判定是可接受的：它们校验的是**协议契约**（合法 JSON、正确工具名），契约不因基线而变；但仍建议在两侧都失败时降级为「均不支持」而非直接判候选 fail（与红旗 §5.2 的 D8 通过率 0% 逻辑对齐）。

### 4.4 维度聚合（`aggregate_dimension`）

各维度用**不同的聚合指标**，而非统一通过率——因为每个维度关心的量纲不同：

- **D1**：`max_tokens` 违规率分级 [5,20]%，叠加整体 pass_rate；
- **D2**：偏差**均值**分级 [1,2]%，同时记录**最大偏差**（喂给红旗）；
- **D8**：**候选 vs 基线的 pass_rate 差**分级 [5,10]pp——这是唯一显式做了相对聚合的维度（`ref_verdict` 与 `verdict` 对比）；
- **D9**：行为匹配率分级 [95,80]%（越高越好）。

四态色：`green`（等价）/ `yellow`（可疑）/ `red`（不等价）/ `gray`（无证据）。阈值全部集中在 `DEFAULT_CONFIG.thresholds`，可被 run 级 config 覆盖（`build_config` 做三层合并）。

## 5. 结论机制

### 5.1 四级结论优先级

```
不可比  ←  闸门不过 OR 任一维度 gray          （证据问题，最高优先）
不等价  ←  存在红旗 OR 任一维度 red
可疑    ←  ≥2 个维度 yellow
等价    ←  其余
```

### 5.2 红旗（一票否决，`enable_red_flags`）

某些差异一旦出现即为强证据，不参与「多数维度绿就算等价」的投票：

- D2 tokenizer 最大偏差 >2% → 「上游很可能不是同一套 tokenizer/模板」；
- D1 `max_tokens` 违规率 >20% → 系统性不遵守；
- D9 孤儿/异常 tool 序列（`D9-orphan-tool`/`id-mismatch`/`dangling-call`）行为与官方不同；
- D8 候选通过率 0% 而基线 >0% → 工具/结构输出完全不可用。

红旗直接把结论顶到「不等价」，即便其余维度全绿。

### 5.3 加权分（`enable_weighted_score`）

`green=100 / yellow=60 / red=0`，按维度权重归一化：`Σ(score·weight)/Σweight`。`gray` 维度不计入（既不加分也不占权重），因此分数只反映**有证据的维度**。分数是辅助参考，**结论以四级判定为准**——避免「高分掩盖单点红旗」。

## 6. 执行与调度

### 6.1 单用例执行（`executor.py`）

- 支持流式 / 非流式，统一产出 `{status_code, behavior_class, usage, prompt_tokens, completion_tokens, output_text, tool_calls, raw_response, param_notes, latency, ttft, error}`；
- `raw_response` 截断到 100KB、`output_text` 截断到 8KB，带 `*_truncated` 标记，便于前端展示原始证据又不撑爆库；
- `behavior_class` 由 `classify(status, error)` 得出：4xx→REJECT、200→ACCEPT_AS_IS、5xx→ERROR_OTHER、异常→UNKNOWN。

### 6.2 调度（`runner.py`）

- 基线与候选各自是独立 `asyncio.Task`，进度写内存 `_progress`，前端轮询；
- 逐用例**串行**执行（一致性测试用例少、重可比性不重吞吐，串行避免限流干扰指纹）；
- `CancelledError` 单独捕获（用户中止），与 `Exception`（失败）区分落库；
- `recover_stale_tasks` 在重启后把遗留 `running` 统一标记 failed（内存 Task 不会续跑）。

### 6.3 数据模型（`store.py`）

`parity_baselines` / `parity_baseline_items` / `parity_runs` / `parity_run_items` 四表。基线 item 存 `payload_json`（发出的请求体，供复现），run item 不重存 payload（与基线同批用例）。报告整体序列化进 `parity_runs.report_json`。

## 7. 配置项（`DEFAULT_CONFIG`）

| 键 | 默认 | 说明 |
|----|------|------|
| `enable_weighted_score` | true | 是否算加权分 |
| `enable_red_flags` | true | 是否启用一票否决 |
| `baseline_max_age_days` | 30 | 基线超期天数 |
| `weights` | 见 DIMENSIONS | 各维度相对权重 |
| `thresholds.D1_max_tokens_violation` | [5,20] | 违规率 %，绿/黄门槛 |
| `thresholds.D2_tokenizer_deviation` | [1,2] | 偏差 %，绿/黄门槛 |
| `thresholds.D8_pass_rate_diff` | [5,10] | 通过率差 pp |
| `thresholds.D9_behavior_match` | [95,80] | 匹配率 %（越高越好）|

三层合并：`DEFAULT_CONFIG` ← run 级 `config` ← `weights`/`thresholds` 子字典单独合并（`build_config`）。

### 8.1 判定可信度自检清单（评审新增用例/规则时对照）

1. 该规则是否**相对于基线**判定？若做绝对判定，是否属于「协议契约」类可豁免（§4.3）？
2. 运维故障是否被 `_operational_failure` 正确拦成 `inconclusive`，而非误算 fail？
3. 缺字段时是否返回 `skip` 而非 fail（不污染分母）？
4. 新维度是否给出了聚合指标与阈值，避免退化成 `gray`？
5. 是否需要红旗（差异是否为「一票否决」级强证据）？
