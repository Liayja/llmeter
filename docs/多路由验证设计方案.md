# 多路由验证设计方案（路由检测 v2）

> 目标：在只有 Base URL + API Key 的黑盒条件下，从平台侧验证上游是否为同一个模型配置了多个路由渠道，并给出渠道数量、权重和证据链的可信估计。
>
> 本方案是现有「路由检测」模块（v1，`app/services/route_probe/`）的升级设计。v1 已实现被动指纹采集与加权判定；v2 补齐主动探针、联合聚类和统计检验。

## 1. 问题定义

上游（中转站 / 聚合网关，如 one-api、new-api 类）通常对同一个对外模型名绑定多个后端渠道，按权重、优先级或健康度分发。客户端无法读取渠道表，只能通过每次请求的可观测差异反推。

平台要回答三个递进的问题：

1. **有没有**：同一模型、同一 Key 的请求是否命中了不止一种后端？
2. **有几个、各占多少**：能否估计渠道数量 k 和各渠道权重 w_i（带置信区间）？
3. **怎么分的**：分流策略是随机加权、按连接粘滞、按时间段切换，还是失败转移（failover）？

## 2. 可观测差异的层级模型

黑盒条件下，一次请求可产生四层差异信号，层级越深越接近"不同模型渠道"这一结论：

| 层级 | 信号 | 采集字段 | 说明 |
|---|---|---|---|
| L1 传输/入口 | 远端 IP、`server`/`via`、HTTP 版本、TLS 特征 | `remote_ip`、响应头 | 可能只是 CDN/边缘变化，弱证据 |
| L2 网关 | 响应 `id` 前缀、`x-request-id` 格式、限流头、错误 JSON 结构 | `id_prefix`、`response_headers`、错误 body | 区分不同网关/推理框架实现 |
| L3 推理栈 | `system_fingerprint`、logprobs、参数支持矩阵、错误文案 | `system_fingerprint`、`logprobs_hash` | 区分 vLLM/sglang/TGI/官方等 |
| L4 模型行为 | `prompt_tokens`（tokenizer）、贪心解码输出、`response.model` | `prompt_tokens`、`output_hash`、`response_model` | 最接近"不同模型/量化/模板"的证据 |

v1 已采集全部四层的大部分字段；v2 的核心是**主动制造 L2～L4 差异被放大的请求**，并把信号做联合分析。

## 3. 总体思路

```text
被动指纹（v1 已有）
    ↓ 不足以区分时
主动探针（v2 新增）：确定性输出 / tokenizer 向量 / 错误指纹 / 参数矩阵 / 缓存 / 连接粘性
    ↓
联合指纹聚类 → 路由候选（route candidates）
    ↓
统计检验：权重估计 + 置信区间、序列平稳性、样本量充分性
    ↓
结论：SINGLE / MULTI(k, weights) / SUSPECTED / EDGE / UNSTABLE / INCONCLUSIVE
```

## 4. 主动探针设计

每种探针是一个独立的请求批次，attempts 增加 `probe_kind` 字段标记来源。探针可单独运行，也可编排为「多路由验证套件」预设。

### 4.1 确定性输出探针（deterministic-output）

- 参数：`temperature=0`、`seed=42`（若支持）、`unique_prefix=false`、固定短 prompt（如要求输出固定 JSON 或做一道算术题）、`max_tokens=16`。
- 信号：`output_hash` 分组。相同 greedy 请求在同一后端上输出高度稳定；跨不同模型实现/量化版本时几乎必然分裂。
- 现状：v1 executor 已计算 `output_hash`（`executor.py:191`），但 `analysis.py` 未将其纳入信号——v2 直接补上。
- 注意：GPU 非确定性会造成同一后端偶发不同输出，因此定为**中强信号（+20）**，且要求每组占比 ≥10% 才计入，避免长尾噪声。开启 `unique_prefix` 时强制置 0（同 prompt_tokens 的处理，见 `analysis.py:124`）。

### 4.2 Tokenizer 向量探针（tokenizer-vector）

- v1 的 Tokenizer 指纹只用单一 prompt 的 `prompt_tokens`。v2 改为**一组 5～8 条精心构造的探针文本**（中英混排、罕见 Unicode、连续空格、代码块、emoji、数字串），每条各发 N 次。
- 信号：每次请求得到一个 `prompt_tokens`，按探针文本对齐后组成向量，例如 `(37, 512, 89, 41, 66)`。向量整体聚类，比单点更鲁棒——不同 tokenizer 在多条文本上同时巧合相等的概率极低。
- 成本：每条 `max_tokens=1`，总消耗可忽略。

### 4.3 错误指纹探针（error-shape）

- 主动发送边界/非法请求，观察错误响应的**结构与文案**：
  - `max_tokens: -1` 或超大值；
  - 未知参数（如 `"nonexistent_param": true`）；
  - 非法 role、空 messages；
  - 超出 context 长度的输入（可选，成本高）。
- 信号：`(status_code, error.type, error.code, message 归一化模板)` 的组合哈希。vLLM、sglang、TGI、官方 API 的错误 JSON 结构和文案差异非常明显，且**不消耗生成 token，几乎零成本**。
- 归一化：错误 message 中的数字、UUID、模型名替换为占位符后再哈希，避免动态内容干扰分组。
- 注意：部分网关会统一改写错误体，此时该信号自然退化为单组，不产生误报。

### 4.4 参数支持矩阵探针（param-matrix）

- 逐个携带 `seed`、`n=2`、`logit_bias`、`top_k`、`response_format={"type":"json_object"}` 等参数发送最小请求。
- 信号：每个参数的结果归为「生效 / 静默忽略 / 报错」，组成支持向量。不同推理栈的支持面差异大。
- 判定辅助：同一渠道对同一参数的行为应稳定；同参数在多次请求间行为跳变本身就是多路由的证据。

### 4.5 缓存探针（cache-probe）

- 同一条较长 prompt（约 2k token）背靠背发 2×M 组，间隔数秒。
- 信号：`usage.cached_tokens`（或 `prompt_tokens_details.cached_tokens`）是否命中、二次请求延迟是否骤降。若"部分请求命中缓存、部分永远不命中"稳定分组，说明请求落在了不同实例/渠道（缓存不共享）。
- 该探针同时区分 `MULTI_INSTANCE`（同渠道多实例，模型指纹一致但缓存不共享）与 `MULTI_ROUTE`。

### 4.6 连接粘性探针（connection-affinity）

- 两个批次对比：
  - A 批：单个 `httpx.AsyncClient` 复用 keepalive 连接连续发 N 次；
  - B 批：每次请求新建连接（`Connection: close` 或每次新 client）发 N 次。
- 信号：若 A 批指纹恒定而 B 批分裂，说明分流决策在**连接层**（LB 四层粘滞）；若两批同样分裂，分流在**请求层**（网关按请求选渠道）。这直接回答"怎么分的"。

### 4.7 多轮时间调度（time-rounds）

- v1 文档建议手动在不同时段跑三轮；v2 平台化：创建 run 时可勾选「定时多轮」，由后端调度器在 T+0、T+4h、T+8h…自动重跑相同配置（复用现有 `job_runner` 基建）。
- 信号：轮与轮之间指纹集合的增减 → 渠道健康切换、权重调整、自动禁用。

## 5. 分析算法升级

### 5.1 联合指纹聚类（route candidates）

v1 对每个维度独立分组再加权求和，无法回答"到底有几个渠道"。v2 增加联合分析：

1. 对每个成功 attempt 构造指纹元组：
   `fp = (channel_header, response_model, system_fingerprint, prompt_tokens_bucket, id_prefix, error_shape, output_hash_bucket)`；
   缺失字段记为通配 `*`。
2. 按元组做**层次合并**：两个元组若在所有非通配维度上一致则合并为同一候选（处理"部分请求头被剥离"导致的字段缺失）。
3. 每个候选输出：样本数、权重估计 `w_i = n_i/N` 及 Wilson 95% 置信区间、延迟 p50/p95、失败率、TTFT 分布、样例请求序号。

产物是一张「路由候选表」，直接对应用户想要的"上游可能配了 k 个渠道，权重大约是 …"。

### 5.2 分流策略判定（序列分析）

对候选路由标签序列（按 `sequence` 排序）做：

- **游程检验（runs test）**：标签随机交错 → 随机加权分流；游程显著偏长 → 粘滞或时间段切换。
- **失败转移检测**：统计"错误之后下一请求切换候选"的条件概率，显著高于基线 → failover 策略。
- **转移矩阵**：k×k 转移计数，展示在前端热力图（可后置到 P3）。

### 5.3 样本量与检出能力

- 检出权重为 p 的次要渠道至少出现一次所需样本量：`n ≥ ln(α)/ln(1-p)`（α=0.05 时，p=5% 需约 59 次）。
- 界面在结论旁展示："当前样本量 N=100，可以 95% 置信检出权重 ≥3% 的渠道；未发现分裂 ≠ 一定单渠道。"
- `INCONCLUSIVE` 的阈值从写死的 `total < 30`（`analysis.py:149`）改为按目标检出权重反推。

### 5.4 判定与置信度调整

在 v1 权重表基础上新增/调整：

```text
渠道响应头多组：           +35（不变）
模型标识多组：             +25（不变）
tokenizer 向量多组：       +25（由单点 prompt_tokens 升级）
logprobs 多组：            +25（不变）
确定性输出多组：           +20（新增）
错误指纹（主动探针）多组： +20（新增）
参数矩阵行为跳变：         +15（新增）
入口指纹多组：             +15（不变）
缓存命中分组：             +10（新增，主要用于区分 MULTI_INSTANCE）
错误阶段多组：             +10（不变）
```

结论枚举沿用 v1 的七种，`MULTI_ROUTE_LIKELY` 附带 `route_candidates`（k、权重、CI）；新增 `routing_strategy` 字段：`random_weighted / sticky_connection / time_based / failover / unknown`。

## 6. 数据模型与接口改动

### 存储（`store.py`）

- `route_probe_attempts` 增加列：`probe_kind`（quick/tokenizer_vector/error_shape/param_matrix/cache/affinity）、`probe_variant`（探针文本编号/参数名）、`connection_reused`（bool，粘性探针用）。
- `route_probe_runs.summary_json` 内嵌 `route_candidates`、`routing_strategy`、`detectable_weight`；`config` 增加 `plan`（探针编排列表）。
- 新增轮次关联：`parent_run_id` + `round_index`，多轮调度的各轮共享对比视图。

### API（`app/routers/route_probe.py`）

```text
POST /api/route-probe/runs            body 增加 plan / schedule 字段（向后兼容）
GET  /api/route-probe/runs/{id}       summary 返回 route_candidates 等新字段
GET  /api/route-probe/runs/{id}/compare?with={other_id}   两次运行的候选表对比（P3）
```

### 前端（`RouteProbeView.vue`）

- 新预设「多路由验证套件」：错误指纹(6) → 确定性输出(30) → tokenizer 向量(6×8) → 缓存(2×4) → 粘性(2×20)，页面显示总成本预估（沿用现有 token 预估与高成本护栏）。
- 结论区新增「路由候选表」：每行 = 一个候选渠道，展示指纹组合、样本数、权重±CI、p50 延迟、失败率、样例序号；导出报告同步包含。
- 新增「分流策略」标签与一句话解释。

## 7. 实施阶段

| 阶段 | 内容 | 说明 |
|---|---|---|
| P1 | 把 `output_hash`、错误体结构纳入现有 analysis；实现联合指纹聚类与路由候选表；样本量提示 | 纯分析层改动，不改请求路径，收益最快 |
| P2 | 主动探针编排（错误指纹、tokenizer 向量、参数矩阵、缓存、粘性）；`probe_kind` 落库；套件预设 | executor/runner/前端联动 |
| P3 | 多轮定时调度、轮间对比、序列检验与转移矩阵可视化 | 依赖 P1/P2 数据 |

## 8. 限制与免责

1. 一切结论仍是**客户端黑盒推断**：网关可以统一改写错误体、剥离响应头、归一化 `model` 字段，使多渠道对外不可见；"未检出"不等于"单渠道"。
2. 确定性输出受 GPU 非确定性影响，只能作中强信号，不能单独定论。
3. 同一渠道滚动升级（模型版本、推理框架版本）也会产生指纹分裂，多轮时间调度可帮助区分"持续并存"与"一次性切换"。
4. 错误指纹探针会向上游发送非法请求，说明文案需提示用户：仅对自有/授权测试的接入点使用，且请求量极小。
5. 缓存字段（`cached_tokens`）并非所有上游返回，探针需容忍字段缺失。
